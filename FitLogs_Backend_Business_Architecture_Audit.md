# FitLogs Backend Business & Architecture Audit

**Repository:** `IvanTran0101/FitLogs`  
**Requested ref:** `main`  
**Actual analyzed ref:** `master`  
**Pinned commit:** [`aeb0f851f7b55e147f3738927fc5c30ae23fb55a`](https://github.com/IvanTran0101/FitLogs/commit/aeb0f851f7b55e147f3738927fc5c30ae23fb55a)  
**Analysis date:** 2026-08-09  
**Repository mutation:** None

## Executive assessment

FitLogs already contains the backbone of a credible MVP: identity through ABP/OpenIddict, a public exercise catalog, user-owned workout plans, a resumable active workout aggregate with set logging, food products backed by Open Food Facts, food logs that snapshot nutrition, and a daily dashboard.

The highest-value next step is not a framework migration. It is to make the existing workflows trustworthy. Four issues currently block that:

1. **Nutrition calculation is wrong for most declared units.** `FoodLogManager.CalculateNutrition` always uses `quantity / 100`, while `FoodUnit` also declares `Milliliter`, `Serving`, and `Piece`. The selected unit has no effect on the calculation.
2. **Food authorization does not match the permission model.** Food product permissions exist in `FitLogsPermissions` but are not registered by `FitLogsPermissionDefinitionProvider` and are not applied to `FoodProductAppService`. Barcode lookup has no `[Authorize]` attribute. Any authenticated user can currently mutate shared food products, while lookup appears callable without authentication.
3. **The workout state machine is only partially implemented.** The model stores exercise status and the current exercise, but it never marks an exercise completed, can leave the current pointer referencing a removed child, and can restart navigation at a skipped exercise after the pointer becomes null.
4. **Custom business tests and CI are effectively absent.** The visible tests are ABP template samples. The most important invariants therefore have no regression protection.

The recommended evolution is incremental: establish a contract/test/security baseline, correct nutrition units and authorization, harden workout/onboarding workflows, then add resilience and progress features. Do not split the monolith, introduce a broker, Event Sourcing, or Redis at this stage.

# Phase 1 — Business discovery

## 1. Product mission

### Verified product behavior

FitLogs lets a person:

- discover exercises by muscle group, equipment, difficulty, and tracking type;
- build and activate reusable workout plans;
- start a plan-based or free workout session;
- add exercises and sets, record reps/weight/RPE, complete or uncomplete sets, navigate the active workout, and complete/cancel it;
- search or create food products, import a product by barcode from Open Food Facts, and keep imported data locally;
- log consumed food and retain a nutrition snapshot;
- review daily calorie/macronutrient and workout totals.

Evidence: [`ExerciseAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Exercises/ExerciseAppService.cs), [`WorkoutPlanAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Workouts/WorkoutPlanAppService.cs), [`WorkoutSessionAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Workouts/WorkoutSessionAppService.cs), [`FoodProductLookupAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Foods/FoodProductLookupAppService.cs), [`FoodLogAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Foods/FoodLogAppService.cs), and [`DashboardAppService`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application/Dashboards/DashboardAppService.cs).

### Core value proposition — reasonable inference

FitLogs is intended to reduce the friction of daily fitness self-tracking by combining workout execution and food logging in one mobile-oriented product. Its strongest differentiator inside the current code is continuity: plans become sessions, sessions preserve historical targets/sets, food products become immutable-enough log snapshots, and the dashboard joins both domains for a selected day.

### Primary user outcomes

1. Know what to train and execute the workout without losing place.
2. Preserve actual set performance for later review.
3. Add packaged food quickly through barcode lookup.
4. See a trustworthy daily nutrition/workout summary.
5. Reuse and adjust plans over time without corrupting history.

### Likely MVP boundary

**Inside the current MVP:** account/authentication, user profile, exercise browsing, workout-plan CRUD and activation, active workout/session logging, food-product lookup/search, food-log CRUD, daily summary, basic mobile UI.

**Future or secondary:** weekly/monthly progress, weight history, streaks, recommendation/coaching, social sharing, rich administration, true offline mutation/sync, notifications, advanced analytics. The React dashboard currently hard-codes streak/progress/weight cards, but no corresponding backend capability exists.

## 2. User types

### Anonymous visitor — verified

- **Goals:** browse the exercise library before signing in.
- **Allowed:** `ExerciseAppService.Get/GetBySlug/GetList/GetSelectableList`, muscle-group reads, and equipment reads are explicitly `[AllowAnonymous]`.
- **Unexpectedly allowed:** `FoodProductLookupAppService` has no authorization attribute; unless a global fallback policy exists outside the inspected code, barcode lookup is public.
- **Restricted:** workout plans, sessions, profile, dashboard, food logs, and food-product service require authorization/permissions.

### Authenticated fitness user — verified with one permission-grant unknown

- **Goals:** maintain a profile, create owned plans, run one active session, log food, and review daily results.
- **Owned resources:** `UserProfile`, `WorkoutPlan`, `WorkoutSession`, `FoodLog` are tied to `CurrentUser.GetId()` and owner-checked on sensitive reads/mutations.
- **Shared resources:** exercises, muscle groups, equipment, and food products are global/shared; no `UserId` is stored on them.
- **Restrictions:** cannot access another user's plan/session/log. Starting a plan-based session requires ownership, plan activation, and active exercises. Only one in-progress session per user is allowed in both domain logic and a filtered unique PostgreSQL index.
- **Unknown:** which FitLogs permissions are granted automatically to a newly registered user. Definitions exist, but grants were not visible.

### Catalog administrator / permission holder — verified as a security model, not as a named role

- **Goals:** create/update/activate/deactivate exercises, muscle groups, and equipment; likely curate and verify food products.
- **Evidence:** granular permissions exist for exercise catalog operations and food products in [`FitLogsPermissions`](https://github.com/IvanTran0101/FitLogs/blob/master/src/FitLogs.Application.Contracts/Permissions/FitLogsPermissions.cs).
- **Ambiguity:** no FitLogs-specific `Admin` role is declared. ABP Identity/SaaS host administrators exist as infrastructure roles. Food-product permissions are not actually registered/applied.

### Host/tenant administrator — framework capability, not established product persona

ABP Pro Identity, SaaS, impersonation, audit logging, and tenant administration modules are installed. This proves administrative infrastructure exists, but not that multi-tenant gym/coaching organizations are part of the intended FitLogs business model.

## 5. User journeys

### 5.1 New user registration and onboarding

- **Entry:** React `login()` redirects to the configured OpenIddict authority via `oidc-client-ts`; ABP Account provides identity UI.
- **Backend:** ABP Account/Identity/OpenIddict, seeded public client `FitLogs_App`, authorization-code flow.
- **Domain:** `IdentityUser`; intended extension is `UserProfile`.
- **Verified rules:** profile read/update requires FitLogs profile permission and operates only on `CurrentUser`.
- **Failure cases:** OIDC config/redirect mismatch; missing permission grant; `UserProfileNotFound` after successful login.
- **Missing:** no verified profile creation event handler or explicit create endpoint; React profile form is not wired to the backend and contains fields not represented by the backend (`Protein`, activity level).

### 5.2 Exercise discovery

- **Entry:** `/exercises`, `/exercise-picker`, or plan add-exercise route.
- **API calls verified in React:** `GET /api/app/exercise`, `/api/app/exercise/selectable-list`, `/api/app/muscle-group`, `/api/app/equipment`, and exercise detail/by-slug.
- **Objects:** `Exercise`, `MuscleGroup`, `Equipment`.
- **Rules:** selectable list forces active exercises; catalog uniqueness is backed by slug, muscle/equipment names/codes, and `(Exercise.Name, EquipmentId)` indexes.
- **Failure cases:** missing exercise/reference; inactive references; pagination cap hides items because React performs client-side filtering after the first 100/200 results.
- **Missing:** server-side search interaction in React, media fallback, admin UI.

### 5.3 Workout plan creation

- **Entry:** React `/plans/new`.
- **Backend:** `WorkoutPlanAppService.CreateAsync` then add exercises through `AddExerciseAsync`; update/activate is separate in behavior even though not separate in the contract.
- **Objects:** `WorkoutPlan`, `WorkoutPlanExercise`, referenced `Exercise`.
- **Rules:** unique name per user, user ownership, inactive exercise cannot be added, no duplicate exercise/order, archived plans cannot mutate, activation requires at least one exercise.
- **Failure cases:** duplicate name/order/exercise, inactive exercise, missing permission, activation of empty plan.
- **Missing/contract defect:** `CreateWorkoutPlanDto.IsActive` is ignored. New plans are always inactive. The React picker adds multiple exercises sequentially, so partial completion is possible if a later request fails.

### 5.4 Starting a workout session

- **Entry:** backend `WorkoutSessionAppService.CreateAsync`; no working React entry yet.
- **Objects:** `WorkoutSession`, snapshot `WorkoutSessionExercise` children, optional source `WorkoutPlan`.
- **Rules:** one in-progress session per user; plan must belong to user and be active; all plan exercises must be active; target values are copied into the session.
- **Reliability:** domain pre-check plus PostgreSQL filtered unique index; repository translates the unique violation to `UserHasInProgressWorkoutSession`.
- **Failure cases:** existing active session, plan not found/not owned/inactive, inactive exercise.
- **Missing/contract defect:** `CreateWorkoutSessionDto.Name` is required but ignored for plan-based sessions. No idempotency key prevents duplicate client retries beyond the active-session invariant.

### 5.5 Updating exercise sets

- **Entry:** add/update/remove/complete/uncomplete methods on `IWorkoutSessionAppService`.
- **Rules:** session must be in progress; session ownership; unique positive set number; non-negative weight; positive reps; RPE 1–10 in domain.
- **Failure cases:** wrong owner, finished session, missing child/set, duplicate number, invalid values, completing an already completed set.
- **Mismatch:** `UpdateExerciseSetDto` permits RPE `0`, while the domain rejects it.
- **Missing:** duration/distance set shapes despite exercise tracking types that require them; optimistic API conflict handling in clients.

### 5.6 Completing or cancelling a workout

- **Entry:** `CompleteAsync` or `CancelAsync`.
- **Rules:** only an in-progress owned session; end time cannot precede start time.
- **Delete semantics:** deleting an in-progress session cancels it rather than deleting; completed sessions cannot be deleted; cancelled sessions are physically deleted.
- **Missing/ambiguity:** session can be completed with zero exercises or no completed sets; exercise `Completed` status is unused; current pointer is not cleared on completion/cancel.

### 5.7 Searching for a food product

- **Entry:** `FoodProductAppService.GetListAsync` with text filter.
- **Objects:** shared `FoodProduct` catalog.
- **Rules:** defaults to active products; filter matches name, brand, barcode.
- **Failure cases:** auth failure, no result.
- **Missing:** React API/UI, locale/brand normalization, relevance ranking, paged server-driven search UX.

### 5.8 Scanning a barcode

- **Entry:** `FoodProductLookupAppService.LookupByBarcodeAsync`.
- **Flow:** trim barcode → local lookup → Open Food Facts on miss → validate/create shared product → save → return lookup result.
- **Rules:** barcode required; database unique filtered index prevents duplicate non-null barcodes.
- **Failure cases:** missing product/name, network timeout/non-success response, concurrent import unique violation, invalid non-numeric code accepted until external failure.
- **Missing:** React camera/scanner integration, explicit authorization, freshness policy, graceful external-error response, data-quality flag.

### 5.9 Adding food to a daily log

- **Entry:** `FoodLogAppService.CreateAsync`.
- **Objects:** active `FoodProduct` and new user-owned `FoodLog` snapshot.
- **Rules:** authentication, valid product, positive quantity, valid meal/unit, non-negative nutrition; optional macro overrides.
- **Critical failure:** calculation is `quantity / 100 × per100g` for every `FoodUnit`. A `1 Serving` or `1 Piece` log is therefore calculated as 1% of the per-100g value.
- **Missing:** conversion metadata and override provenance.

### 5.10 Reviewing daily nutrition totals

- **Entry:** `FoodLogAppService.GetDailySummaryAsync` or dashboard daily/today methods.
- **Rules:** only current user's logs in `[date, date + 1 day)`; sum nutrition snapshots; dashboard includes calorie target/remaining and meal breakdown.
- **Failure cases:** incorrect totals caused by unit calculation; user/server time-zone boundary mismatch; missing profile calorie target.
- **Frontend:** dashboard is hard-coded and not integrated.

### 5.11 Editing and deleting food logs

- **Entry:** `UpdateAsync`/`DeleteAsync`.
- **Rules:** owner-only; update recalculates from current product data, then applies overrides.
- **Failure cases:** wrong owner, inactive/missing product, invalid input.
- **Ambiguity:** editing an old log can silently replace its historical nutrition snapshot with newer product data.

### 5.12 Viewing workout or nutrition history

- **Workout:** paged list supports status, plan, date range, text, and sorting. Detailed sets require a subsequent `GetAsync`.
- **Nutrition:** exact-day log list and exact-day summary only.
- **Frontend:** not implemented.
- **Missing:** weekly/monthly read models, cursor/date navigation UI, body-measurement history, and an explicit historical-snapshot policy.

# Phase 2 — Backend codebase audit

## Architecture map

The active code is a **layered ABP monolith**, not yet a physically modular monolith with independently packaged business modules. Business capabilities are separated mainly by namespaces/folders inside shared Domain/Application/EF projects. This is adequate for the MVP and should not be rewritten.

```text
React or Blazor client
  → ABP conventional HTTP API controllers
  → Application services + permissions/owner checks
  → Domain aggregates and domain managers
  → EF Core repositories / PostgreSQL
  → Mapperly/ObjectMapper DTOs
```

External calls flow from `FoodProductLookupAppService` through `IOpenFoodFactsClient` to the `FitLogs.ExternalServices` typed `HttpClient`.

## Domain rules and invariants

### Strongly enforced

- One profile row per user through a unique DB index.
- Unique exercise slug; unique `(name, equipment)`; restricted FK deletion for referenced muscle/equipment.
- User-owned plans and sessions; log ownership checks.
- Unique plan name enforced by manager (application race still possible because no matching DB unique index).
- Archived plan cannot mutate; active plan must contain an exercise.
- Unique exercise and order within a plan/session; unique set number within a session exercise.
- Only one in-progress session per user, protected at application/domain and DB levels.
- Session mutation requires `InProgress`.
- Completed sessions cannot be deleted.
- Food log stores nutrition/name snapshot and references a non-deletable product.
- Non-null barcode uniqueness through a filtered unique index.

### Weak or missing

- Plan-name uniqueness has no DB constraint, so concurrent creates can violate the intended invariant.
- Food unit/serving conversion is not modeled.
- Barcode validation only checks non-empty text.
- Imported nutrition can silently treat missing calories as zero.
- Current session exercise pointer has no FK and is not repaired on child removal.
- Session-exercise `Completed` status has no transition.
- Session completion has no completeness rule.
- Food override provenance and reason are not recorded.
- `WorkoutGoal`/`WorkoutDifficulty` setters do not validate defined enum values.
- User profile enum setters do not validate defined values.

## Persistence and migrations

- PostgreSQL with EF Core; aggregate children cascade from plan/session, while sessions restrict deletion of referenced plans and logs restrict deletion of food products.
- Indexing is generally aligned with current queries: user/date food logs, active-session uniqueness, barcode, session/plan children.
- Three custom migrations are visible: the large initial schema, current-exercise/archive/status additions, and unique active-session index.
- `CurrentWorkoutSessionExerciseId` is indexed but not configured as a foreign key.
- A stale duplicate solution and duplicate Docker definitions create migration/deployment ambiguity.

## Authentication and authorization

### Verified strengths

- OpenIddict local validation and authorization-code client configuration.
- Bearer forwarding, dynamic claims, permission definitions, ownership checks.
- React attaches bearer tokens and uses explicit redirect callbacks.

### Verified gaps

- Food-product permission constants are absent from the definition provider and unused in services.
- Barcode lookup/refresh has no explicit authorization.
- Global anti-forgery auto-validation is disabled while the host supports cookies and React sends `credentials: include`. This requires a deliberate token-only API policy or restoration of CSRF protection.
- Development-style static certificate/string-encryption/database credentials are committed in configuration files. Values are intentionally omitted here. They must not be treated as production secrets.
- PII logging is enabled by default in checked-in appsettings (`DisablePII: false`), unsafe for production if not overridden.

## Background jobs, caching, events, logging, error handling

- ABP background-job and audit-log modules/tables are installed, but no FitLogs-specific background job was found.

- Serilog console/file sinks and ABP audit logging are configured; no domain-specific metrics or structured dashboards were found.

# Incremental backend upgrade plan

## Phase A — Baseline, repository hygiene, and security (P0)

### A1. Establish one source tree and one branch convention

- Confirm that the root solution is canonical.
- Remove or archive the nested `FitLogs/` copy in a dedicated change after comparison.
- Decide whether to rename `master` to `main` or update all documentation/automation to `master`.
- Align Docker/OpenIddict names and ports with root appsettings.

**Acceptance:** one solution file, one migration chain, one Docker definition, and documented startup commands.

### A2. Add a behavior-focused test baseline and CI

Add tests before changing business rules:

- Food calculation table tests for every supported unit.
- Owner/permission tests for plans, sessions, food logs, and shared catalog mutation.
- Two concurrent session starts produce one success and one domain error.
- Two concurrent imports of one barcode return the same product.
- Workout navigation/removal/completion transition tests.
- Dashboard date-boundary and completed-set aggregation tests.

**Acceptance:** pull requests run build, domain tests, application tests, EF/PostgreSQL integration tests, and React type/lint/build checks.

### A3. Close configuration/security gaps

- Move non-development secrets/passphrases to environment/secret storage; rotate any value used outside local development.
- Default PII logging off; enable only for explicit local debugging.
- Make the API authentication model explicit. If bearer-only, stop sending cookies and enforce it. If cookies remain, do not globally disable anti-forgery validation.
- Register and apply food permissions; add default grants for the normal user role and admin-only catalog actions.
- Require authentication for barcode lookup/refresh unless public access is an explicit business decision; add rate limiting at the host edge/application.

## Phase B — Nutrition correctness and trustworthy daily totals (P0)

### B1. Define a canonical nutrition measurement model

Recommended minimal evolution:

- `FoodProduct.NutritionBasisAmount` (normally 100).
- `FoodProduct.NutritionBasisUnit` (`Gram` or `Milliliter`).
- structured optional serving conversion: numeric `ServingAmount` + `ServingUnit`.
- optional numeric `PieceWeightGrams`; do not parse free-text `ServingSize` for calculations.

Keep `ServingSize` only as display text during migration.

### B2. Make consumption conversion explicit

- For grams against per-100g: direct calculation.
- For milliliters: require per-100ml basis or a density conversion; never assume 1 ml = 1 g globally.
- For serving/piece: require numeric conversion metadata; otherwise return a validation error and let the user log grams/ml or create a custom product.
- Record calculation basis/conversion in the FoodLog snapshot so history remains explainable.
- Decide whether overrides are an advanced feature, a custom-food flow, or admin-only correction. Store override provenance.

### B3. Migration strategy

1. Add nullable basis/conversion columns.
2. Backfill existing products as `100 Gram` only where that is truthful.
3. Deploy read compatibility.
4. Enforce conversion rules in new writes.
5. Audit/recalculate only logs the product owner explicitly chooses; do not silently rewrite historical logs.

## Phase C — Workflow integrity and contract cleanup (P1)

### C1. Complete onboarding lifecycle

- Prefer an idempotent handler for identity-user creation plus a lazy `GetOrCreateMyProfile` safety net or explicit onboarding command.
- Backfill profiles for existing users.
- Keep identity credentials and fitness profile in separate aggregates.
- Reconcile React profile fields with real backend fields; macro targets/activity level require explicit product decisions and schema.

### C2. Complete the workout state machine

- Define transitions for session and session exercise (`Pending → InProgress → Completed/Skipped`).
- Mark current exercise in progress and decide when it becomes completed.
- When removing the current exercise, select the next valid exercise or clear the pointer atomically.
- Navigation must exclude skipped/completed items according to a documented rule and must not restart at the first skipped exercise.
- Decide whether session completion requires at least one completed set/exercise. If permissive, name the behavior explicitly.
- Add a foreign key or aggregate-level invariant for the current-exercise pointer.
- Validate `WorkoutGoal`, difficulty, profile enums, and DTO/domain RPE consistently.

### C3. Make commands intention-revealing

- Replace ambiguous session create semantics with `StartFromPlan` and `StartFreeWorkout` contracts, or conditional validation.
- Remove `IsActive` from create-plan DTO; activation is a separate command because an empty plan cannot activate.
- Declare every public application method in its interface or intentionally hide it from conventional controllers.
- Add batch `AddExercises` to a plan so the React picker is atomic.
- Generate/check the TypeScript client from Swagger. This would have caught the current WorkoutGoal label mismatch and service/interface drift.

## Phase D — Open Food Facts reliability (P1)

- Validate and normalize supported barcode formats; document accepted codes.
- On concurrent cache miss, catch unique violation and re-read the winning product.
- Distinguish `not found`, invalid data, timeout, upstream error, and local failure.
- Preserve missing nutrition as unknown rather than silently converting missing calories to zero.
- Define refresh/freshness rules using `LastSyncedAt`; do not add a background refresh job until traffic/data shows it is needed.
- Add bounded timeout/retry/circuit-breaker behavior only for safe transient failures.
- Send the integration identification headers required by the upstream service and monitor success/latency.

## Phase E — Dashboard and progress evolution (P1/P2)

- Store or resolve the user's time zone; convert local day boundaries to UTC for queries.
- Decide whether workout day means started date or completed date.
- Count completed sets and volume from completed sets if the metric means performed work.
- Use database projections for weekly/monthly aggregates when those screens are added; current one-day in-memory aggregation is acceptable and does not justify Redis.
- Add a `BodyMeasurement` time-series aggregate only when trend tracking is a confirmed requirement. Do not overload `UserProfile.WeightKg` as history.
- Introduce a `WorkoutSessionCompleted` event only when a real asynchronous consumer exists (streaks, achievements, notifications, analytics).

# Over-engineering risks to avoid

- **Do not move to microservices.** Current scale and team needs favor a modular/layered monolith.
- **Do not adopt Event Sourcing/CQRS broadly.** Commands and daily read models are simple; targeted query services are enough.
- **Do not add RabbitMQ/Kafka/outbox without an asynchronous business workflow.** No current requirement justifies it.
- **Do not add Redis for daily dashboard queries.** Correctness and query projection matter before caching.
- **Do not build offline write synchronization casually.** Workout/food conflict resolution and idempotency must be designed first.
- **Do not keep both Blazor and React as equal product frontends indefinitely.** Choose the product UI; retain Blazor only for administration/auth hosting if that is intentional.
- **Do not introduce separate physical ABP modules solely for architectural purity.** First clean namespace boundaries and dependencies; extract only when teams/deployment/reuse require it.

1. Are ordinary users allowed to create shared food products, or only private/custom products?

9. Which permissions are granted to newly registered users in the deployed environment?
10. Is offline logging an MVP requirement or a later enhancement?
